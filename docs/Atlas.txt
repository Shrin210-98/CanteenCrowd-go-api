HOW YOUR WORKFLOW CHANGES
BEFORE — golang-migrate
text
1. Dev wants to add a column
2. Write migration SQL by hand (up + down)
3. Run migrate-up
4. Update db/schema/ manually for sqlc
5. Regenerate sqlc
Two sources of truth: migrations + db/schema. Manual sync.

AFTER — Atlas
text
1. Dev edits db/schema/*.sql (single source of truth)
2. Atlas generates migration automatically
3. Run migrate-up
4. Regenerate sqlc (from same db/schema/)
One source of truth: db/schema. Auto sync.

==========================================================================================
N+1 QUERY PROBLEM EXPLAINED ⚠️
==========================================================================================

WHAT IT IS:
  🔴 An ORM loads parent rows, then for EACH parent, runs a separate query
  🔴 1 + N queries instead of 1-2.

EXAMPLE (GORM):
  users := db.Find(&users)          -- 1 query: SELECT * FROM users
  for _, u := range users {
      db.Find(&u.Requests)          -- N queries: one per user!
  }
  🔴 Total: 1 + 100 = 101 queries for 100 users

EXAMPLE (sqlc):
  -- name: GetUsersWithRequests :many
  SELECT u.*, r.* FROM users u
  LEFT JOIN requests r ON r.requester_id = u.id;
  ✅ 1 query, always

IMPACT:
  🔴 100x slower at scale
  🔴 Database load spikes
  🔴 Hard to notice in dev (small data)
  🔴 Symptoms appear only in production

==========================================================================================
MAGIC BEHAVIOR EXPLAINED 🔮
==========================================================================================

WHAT IT IS:
  🟡 ORMs do things behind the scenes that aren't obvious from your code.

EXAMPLES:
  🔴 GORM auto-creates columns, indexes, foreign keys (silently)
  🟡 Hibernate caches queries, auto-flushes on access
  🟡 TypeORM has cascade behaviors triggered by relations
  🟡 Prisma wraps transactions implicitly

PROBLEMS:
  🔴 Hard to predict exact SQL
  🔴 Difficult to debug production issues
  🔴 Performance surprises
  🔴 Hidden lock contention
  🔴 "Why is this slow?" → grep the ORM source

==========================================================================================
HARD TO OPTIMIZE EXPLAINED 🐌
==========================================================================================

WHY ORMs ARE HARD TO OPTIMIZE:
  🔴 Query planner sees different SQL each time
  🔴 ORM generates subqueries where a JOIN would work
  🔴 Indexes may not match ORM-generated WHERE clauses
  🔴 Eager loading forces you to load entire object graphs
  🔴 Connection pools tuned for ORM, not your workload

RESULTS:
  🟠 Need query-specific overrides
  🟠 Mixed ORM + raw SQL (worst of both)
  🟠 Hard to explain to DBAs
  🟠 Cannot use EXPLAIN ANALYZE meaningfully

WHY SQLC IS EASY TO OPTIMIZE:
  ✅ You write the SQL — you control the plan
  ✅ EXPLAIN ANALYZE gives exact answers
  ✅ Indexes match your WHERE clauses
  ✅ No hidden subqueries

==========================================================================================
AMBIGUOUS GENERATED SQL EXPLAINED ❓
==========================================================================================

WHAT IT IS:
  🔴 When you write ORM code, you're guessing at what SQL will run.

EXAMPLE (GORM):
  db.Preload("Requests").Find(&users)
  ❓ What SQL runs?
  ❓ SELECT * FROM users?
  ❓ SELECT * FROM users WHERE ...?
  ❓ With what indexes?
  ❓ With what lock mode?

YOU CANNOT KNOW without:
  🔴 Turning on GORM's query logger
  🔴 Reading GORM's source
  🔴 Running and inspecting

EXAMPLE (sqlc):
  -- name: GetUsersWithRequests :many
  SELECT u.*, r.* FROM users u
  LEFT JOIN requests r ON r.requester_id = u.id
  WHERE u.is_active = TRUE;
  ✅ You wrote this. It runs this. Zero ambiguity.

CONSEQUENCES:
  🔴 Production bugs impossible to reproduce in dev
  🔴 Slow queries appear without warning
  🔴 Database indexes unused
  🔴 Debugging becomes archaeology
